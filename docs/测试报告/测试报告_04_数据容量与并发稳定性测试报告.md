### 2.4 进一步容量评估（理论推算）

系统使用**链表**存储数据，核心限制因素：

```
链表结构开销: 每个节点约 32-40 bytes (指针 + int + data指针 + id[20])
- 1000患者: 约 1000 × (80+40) = 120 KB
- 10000患者: 约 10000 × 120 = 1.2 MB
- 100000记录: 约 100000 × 120 = 12 MB
```

| 场景   | 数据量               | 预估内存    | 预计响应            |
| ---- |:-----------------:|:-------:|:---------------:|
| 小型医院 | 1000患者/5000记录     | <2 MB   | 即时              |
| 中型医院 | 10000患者/50000记录   | <15 MB  | <1s             |
| 大型医院 | 100000患者/500000记录 | <150 MB | 1-3s (链表遍历O(n)) |

> **结论**: 在10万级数据量下系统仍可正常运行，但`FindNode()`的O(n)遍历在特大级数据（百万以上）可能出现性能瓶颈。

## 四、并发稳定性分析

### 4.1 并发场景分析

> **架构说明**: 当前系统为**单进程单线程控制台应用**，不存在真正的并发执行。

#### 场景1: 多名医生同时为同一患者开具处方

| 风险描述   | 当前架构下的表现                |
| ------ | ----------------------- |
| 数据竞争   | 单线程顺序执行，无竞争条件           |
| 库存超卖   | 每次操作即时扣减，后续操作基于最新值      |
| 余额重复扣减 | 顺序执行，每次扣减立即写入文件         |
| **结论** | **当前架构安全**（单线程模型天然避免竞争） |

#### 场景2: 多名患者同时预约同一医生

| 风险描述   | 当前架构下的表现                                   |
| ------ | ------------------------------------------ |
| 号源超卖   | `current_patients < max_patients`检查在单线程下有效 |
| 排班冲突   | 同一排班在单次执行中串行处理                             |
| **结论** | **当前架构安全**                                 |

#### 场景3: 多实例同时运行（真正的并发风险）

| 风险描述       | 详细信息                                    |
| ---------- | --------------------------------------- |
| 同时写文件相互覆盖  | 两个his_test.exe实例同时运行时，后保存的实例覆盖先前的数据     |
| 数据丢失       | 实例A加载数据→实例B加载同一数据→实例A保存→实例B保存（丢失实例A的更改） |
| ID冲突       | GenerateID依赖自增序列+时间戳，多实例可能生成相同ID        |
| **严重程度**   | 🔴 高风险（不支持多实例并发）                        |
| **建议**     | 引入文件锁机制或使用数据库替代文本文件                     |
| **课程设计说明** | 单用户控制台应用，多实例并发不在设计目标范围内，答辩时可说明此限制       |

### 4.2 事务性分析

| 操作   | 涉及步骤数                   | 原子性   | 说明                |
| ---- |:-----------------------:|:-----:| ----------------- |
| 普通挂号 | 6步（验证→扣费→改状态→加号源→记录→保存） | ❌ 非原子 | 扣费后若崩溃，余额丢失但挂号未完成 |
| 发药   | 6步（验证→扣库存→扣费→记录→保存）     | ❌ 非原子 | 库存扣减后若崩溃，数据不一致    |
| 住院   | 4步（改床位→改患者→记录→保存）       | ❌ 非原子 | 同上                |
| 出院   | 3步（释放床位→改患者状态→保存）       | ❌ 非原子 | 同上                |

> **说明**: 所有操作均先修改内存数据，最后一步才写入文件。如果程序在中间步骤崩溃，内存数据丢失但文件未变（最终保存使用原子写入），因此不会产生损坏的中间状态。

## 八、总体评估

**结论**: HIS医院信息系统在数据容量测试中表现良好，110患者/20医生/20药品/30床位的批量操作全部成功，数据完整性和一致性检查全部通过。系统基于单线程链表架构，在小中型数据规模（<10万条）下运行稳定可靠。

**主要限制**:

1. **不支持多实例并发运行** — 文本文件无锁机制，多实例间数据会相互覆盖（课程设计可接受）
2. **非事务性操作** — 多步业务操作在异常中断时可能出现部分更新（原子写入已缓解文件损坏风险）
3. **O(n)查找性能** — 链表架构导致查找性能随数据量线性增长（课程规模下可忽略）
